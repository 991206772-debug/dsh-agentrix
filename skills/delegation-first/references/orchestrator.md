# 主控执行流程

## 规划

先读刚好够用的上下文，明确目标、修改范围、交付物和验证方式。拆出可独立验收的任务；有依赖的任务写 `dependsOn`，共享文件写入 `writes`，只读任务用空数组。

主控使用对话框选择的高模型确定方案、接口和验收要求，再拆成执行者能明确完成的任务。向用户简要说明拆分与验证方法，然后调用 `delegation_plan`。无需让用户手工派单。`routine/complex` 只标明复杂度和审查需求；执行者始终用 worker 模型，审查者始终用 reviewer 模型，主控负责最终实际验证与验收。

执行模型未配置时暂停，不能自动继承主控；审查模型未配置时明确跟随主控，每次启动固定快照。执行者报告能力不足或未定设计时，补充方案或重新拆分，不自动换高模型执行，也不让它原样反复重试。

先看当前回合的路由结果：`direct` 表示范围小且预计一步完成，`delegate` 表示需要拆分或监督，`delegate_parallel` 表示存在可以并行推进的独立目标。把路由的 `reasons` 和预计步骤作为任务卡设计依据；如果任务卡与路由不一致，先修正拆分或在计划提醒中说明原因。

任务卡应自足：子 Agent 使用新上下文，不会自动读到主控的全部对话。重要输入路径、先前结论和停止条件写进 `instructions`、`scope`。不要把大量原文、完整日志或凭据复制进任务卡。

## 委派与监督

调用 `delegation_run` 后，插件按全局并发上限派出可执行任务，默认同时最多 2 个，所有会话共享名额；每个计划还有独立的总派发预算，默认 8 次，包含返工。前置任务须先验收；修改路径重叠的任务等前一个验收。若任务仍为 `queued`，先读 `delegation_status` 返回的等待原因；有“并发名额”提示时等待即可；有“派发预算已用尽”提示时不要反复调用 `delegation_run`，应新建计划或先处理已有任务，也不能绕过委派闸门直接修改。

插件确认正式报告返回后会通知原主控，再调用 `delegation_status`。新任务采用 `delivery: caller`，子代理通过报告入口交成果，不使用 `send_message`。主控提前结束但仍有任务运行时，插件等待现有任务事件，不反复请求模型查询。执行者在调查、实现或验证阶段用 `delegation_checkpoint` 提交阶段结论、下一步和成功工具 callId；它只是待核实进度，不代表完成。重复错误、长时间没有有效阶段成果、预算接近上限或接近截止时间时，插件会唤醒原主控；主控读取状态和证据后用 `delegation_control({taskId,action:'steer',message})` 纠偏原子代理。预算段达到上限且已有真实进展时，插件会保留证据并自动续跑同一任务；续跑计入计划启动预算，不增加逻辑执行次数。每次执行最多自动纠偏两次；没有进展或启动额度耗尽才阻塞。需要纠偏时：

```js
delegation_control({taskId:'task-a', action:'steer', message:'说明偏离了哪条要求，以及接下来应核对的文件或步骤'})
```

不要边派边做同一项实现，不要反复询问“好了吗”。`stop` 只表示取消，必须提供 `reason`；不能用于成功收尾。已返回任务由插件自动释放，无需再 stop。确需取消时记录原因；处理真实失败后才用 `retry`，并写明已处理哪个问题。

失败不会自动重试。子任务失败或超时后，当前计划暂停后续自动派单，尚未启动的排队任务会标为 `blocked`；先处理失败原因，再对具体任务用 `delegation_control` 的 `retry` 明确重试。每任务的执行总次数包括首次执行，默认最多 2 次。达到上限就报告事实，不再要求“继续优化”。

任务结束后，原生子 Agent activation 会调用 `dispose()` 释放运行资源；DSH 保留子会话历史用于回看，因此顶部子智能体数量不等于当前运行数量。验收页的释放状态用于区分这两者。

## 验证与验收

`running` 表示正在执行，`review` 只表示子 Agent 已返回结果。先读 `execution` 的结构化状态与完整报告路径；缺上下文先补资料，阻塞先处理原因，有疑点需给出处理说明。对每个任务卡验证步骤调用 `delegation_verify`；编号从 0 开始。命令通过 DSH 原有工具与审批管线执行，不绕过宿主限制，也不占主控动手预算。

新建 complex 任务自动安排一个独立只读审查者，`audit` 记录对应执行次数、状态、模型、需求和质量两个结论。主控不能代替审查者提交结果，未通过不能验收。审查同样计入启动预算、并发和时限；失败不会自动重开，处理后用 `delegation_audit({taskId,message:'已处理的原因'})` 明确重试。普通任务可按风险请求独立审查，默认不增加代理。

- 文件与结果必须能读到；仅复述子 Agent 的报告不算核对。
- shell 验证必须前台完成并返回退出码 0；后台任务、报错或无退出码都不算通过。
- 验证全部通过后，为每条 `criteria` 提交一项 finding，含标准编号、主控结论和本次实际证据 `callId`。
- 只引用当前任务本次执行的证据；返工后原证据作废。

```js
delegation_review({
  taskId:'task-a', verdict:'accept',
  findings:[{criterion:0, finding:'逐条说明主控实际核对到的结果', evidence:['填写 delegation_verify 真实返回的 callId']}]
})
```

只有具体失败场景和实际影响才触发返工：

```js
delegation_review({taskId:'task-a', verdict:'rework', issueIds:['填写审查返回的真实问题编号']})
// 主控自己发现的问题，必须引用本次实际验证的 callId（验证失败的证据也可以）。
delegation_review({taskId:'task-a', verdict:'rework', issues:[{
  criterion:0, severity:'important', finding:'缺少约定字段，实际输出见证据', evidence:['本次 delegation_verify 返回的 callId']
}]})
```

不要因为风格偏好或“还能更好”阻止验收。minor 只记录；返工必须带具体问题、标准编号和证据。独立复查逐条返回原问题 `ADDRESSED/NOT_ADDRESSED` 及证据；新重要问题必须说明本次修复如何引入，范围外观察不延长循环。普通任务由主控在最终 accept 时提交 `resolutions:[{id,status:'ADDRESSED',evidence:['新验证 callId']}]` 逐条确认修复。预算段有进展时先自动续跑；达到现有执行次数上限、没有进展或总启动预算耗尽才停止，不能靠换模型或新建代理掩盖。

主控判断内容正确性；插件检查验证、问题和审查证据是否属于当前任务和执行次数。页面还原必须看原稿与同尺寸实际截图，运行问题必须回到原场景，不能用单元测试通过代替。

## 完成与阻塞

最后一次 `delegation_review` 验收通过且通过实际工具管线确认后，插件自动生成 `plan.completion` 交付回执并结束主控回合，不需要再让模型写完成总结。只有全部任务实际验收通过，回执才为“已完成”。测试有结果但未验收仍是未完成。取消、失败、阻塞回执明确列出原因、未完成任务和已验收部分。

有报告却漏验证或验收时，结束钩子在原主控上补齐流程，每个计划最多两次；计数持久化，查询、重复 run 和重新加载都不重置。次数用尽后保留交付物和证据，停止自动续跑。用户取消优先，不唤醒已取消的任务。明确重试后当前回执失效，旧回执留在事件历史中，重新验收后再生成。

宿主可能先显示模型文字再检查结束条件，已经显示的错误句子无法保证撤回。聊天的完成标签、验收页与 Markdown 摘要共同读取程序回执，不通过匹配模型文案判断交付成功。

“任务验收”只展示当前会话的需求与验收；查看成员、执行活动和通讯用 Fleet。主控仍须通过本插件的验证和评审工具提交实际证据。

重新加载时活动任务变为 `blocked`，并保留子 Agent 编号。先 `stop` 并写明取消旧执行的原因，再明确重试或取消整个计划。用 `delegation_cancel` 停止整个计划，记录会保留供核对。已验收任务重复清理保持原结果；历史任务不补造报告或验收。
