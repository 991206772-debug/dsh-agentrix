# DSH Agentrix

小任务直接完成并验证；根据实际范围、风险和可并行工作决定是否委派，不用关键词、评分或操作次数代替语义判断。

主控结合当前消息、前文与真实任务状态确认消息关联和是否委派；插件不按词表分流，也不生成预计步数或置信度。实际是否启动子代理以任务状态为准；任务卡决定边界、依赖和审查要求。

主对话输入框上方的小状态标签显示真实活动，点击看详情。准备读取后，用 `delegation_decide` 的 `relation` 确认消息关联：`new` 新需求、`continue` 继续、`update` 补充或调整方案、`question` 询问进度或普通提问。`new/update` 同时提供 `mode:direct/delegate` 和具体 `reason`；`continue/question` 沿用原决定，不重建任务或重置统计。多条待处理消息提供真实 `messageId` 分别确认，不能猜测或伪造编号。

新委派优先用 `delegation_plan({relation,messageId,decisionReason,start:true,tasks,...})` 一并记录并启动，省去单独 decide/run；不要新开分类代理。同类小修改合为一任务，保留每项验收标准和必要检查；需要独立判断、不同验证或可以独立并行时才拆分，不按文件数量强制拆卡。普通正文不能代替记录，不解析内部思考。遗漏时每条待处理消息最多提醒原主控一次，不要求用户点继续。新需求不取消或覆盖旧代理与计划；确认 `new/direct` 后可以处理不重叠的文件，不能重复修改旧任务产物或把旧回执当成新需求完成。阶段变化、等待或阻塞时简短说明当前动作和下一步。最终托管交付结论来自程序回执。

直接执行时，文件修改失败必须核对原文件并修复；成功读取或生成另一份文件不能代替原修改成功。程序最多提醒原主控补救一次；仍未解决时如实说明未完成项，不再声称全部交付。修改成功后也要核对实际内容是否满足用户要求。

## 执行顺序

1. 结合前文和相关代码，明确目标与可验证的子任务。短句和系统低分都不能证明任务简单；发现跨模块、多个功能或执行步骤增加时主动拆分。由主控理解“继续”等表达的真实含义，不依赖固定措辞。
   准备读取用 `read/grep/glob`；目录和 Git 基线用 `delegation_inspect({operation:'list'|'git_status',directory})`。准备记录用 `delegation_note({kind:'task_plan'|'findings'|'progress',content})`，目录由插件确定并返回，不占业务操作额度。不得把任意业务文件命名为计划文档来绕过委派，也不要反复尝试被阻止的未知 shell。
2. 直接执行时先记录 direct 并完成验证；委派时调用 `delegation_plan` 提交任务卡及 `relation/decisionReason/start:true`。字段和示例见 `references/task-card.md`。不要并行调用判断工具和业务修改，须等保存成功。
3. 主控使用对话框选择的高模型做规划与最终验收，先确定方案、接口与用户要求对应的验收标准，再拆给执行者。不自行添加问题数量、报告篇幅或格式门槛；主控整合已有成果，只有汇总本身有独立工作量时才拆为任务。`complexity: routine/complex` 与 `complexityReason` 说明执行难度；另用 `reviewPolicy: coordinator/independent` 和非空 `reviewReason` 说明审查方式与风险依据。调查量大不自动加审查；权限、破坏性数据操作、并发等高风险工作须独立审查。执行者用 `models.worker`，未选则暂停。独立审查使用该次派发时记录的主控模型与思考强度，保持独立上下文。主控派单只走 `delegation_plan/run`，不可用原生派单绕过约定。
4. 托管模型用 `delegation_models` 查询，不用原生模型名单判断配置失效。`start:true` 与查询共用授权和解析检查，遵守已记录的会话白名单；无白名单时明确标记用户托管配置的兼容来源。复杂任务还检查审查模型，再按依赖、写入范围、并发与预算派单。省略或 `start:false` 仅保存计划。默认每计划最多启动 64 次（含返工和审查，可配置 1~256）；预算耗尽不反复 run。配置失效需处理后继续；解析通过不冒充服务成功，不偷偷换模型或绕过授权，启动前拒绝不消耗执行次数。
5. 短任务只提交最终报告。长调查、阶段转换或阻塞时，执行者或只读审查者可用 delegation_checkpoint 记录结论、下一步和成功 callId，记录不能替代验收。delegation_report 通过工具管线确认后自动结束并通知主控；不用 send_message 交成果，不再修改产物。缺上下文或阻塞先处理原因，有疑点由主控说明处理意见。状态默认只读摘要，完整内容用 delegation_status({taskId,detail:'full'}) 按任务读取。
6. 按工具结果的 `nextAction` 继续。等待时简短告知用户，再调用 `delegation_wait` 或结束当前回复等待通知；不轮询 `status`，依赖任务会在前项验收后自动启动，不重复 `run`。报告、故障或用户新消息会唤醒主控；其他任务仍在运行时，也可先验收已返回的任务。对 `review` 状态任务默认调用 `delegation_verify({taskId})`，一次顺序执行全部检查并返回逐项证据；必要重验时指定从 0 开始的 `checkIndex`。主控仍需阅读结果再验收；沿用宿主取消信号，不增加统一截止时间。
7. `reviewPolicy: independent` 的任务自动安排一个独立只读审查者，审查通过后主控才可验收；`coordinator` 由主控验证验收。未指定时沿用旧约定：complex 自动审查，routine 按需用 `delegation_audit` 请求。审查沿用该次执行的分发者模型，计入同一并发与启动预算；失败后用 `delegation_audit({taskId,message})` 明确重试审查，不重跑实现。返工记录新分发者；审查重试用原记录。
   阅读实际结果，用 `delegation_review` 逐条验收：`criterionId` 复制验证结果提供的 C1、C2，`evidence` 复制本任务本次验证的 `ref`，`finding` 由主控写实际结论。不要拼接编号、加前缀或把文件说明当证据编号。原来的从 0 开始的 `criterion` 和原始 `callId` 仍兼容。返工引用已有 `issueIds` 或提交具体 `issues`；minor 不触发返工，复查只检查原问题和直接回归。routine 返工后用 `resolutions` 引用新证据确认问题解决。测试通过不能替代视觉还原或实际场景证据。
8. 最后一次实际验收通过后，插件自动生成交付回执并结束回合，无需模型再写总结。正常报告通知不消耗补流程次数；主控同一未推进阶段最多补流程两次，子代理每次执行最多补报告两次，计数持久化，超限停止自动续跑。只有全部任务实际验收，回执才为“已完成”；失败、取消和未验收列出真实原因。模型的 403、404 等失败先处理服务或配置问题，不能通过重复调用或自动换模型掩盖。

## 责任边界

- 计划执行中主控不重复改写子任务产物；主控可以读上下文、监督与评审。
- 调用达到 80 次、运行达到配置的提醒时间，只在页面提醒并记录事件，不唤醒模型、不停止、不换代理、不消耗纠偏次数。Token 只统计；输出截断在原代理续接。重复同类失败通知主控，最多两次纠偏后仍重复故障才阻塞。重复成功操作会调查提醒一次，由主控结合新证据、排除的假设和交付物判断是否推进需求；必要时纠正原代理，不把提醒当成失败或自动换代理。不同文件、不同片段与持续输出不会因没写文件被误停。
- 子任务启动时固定模型；设置修改影响之后启动的任务。实际请求在发送前核对，错配会被阻止并暂停计划；不得自动换模型或新建 Agent 掩盖问题。
- 执行者可决定不改变接口、范围和验收要求的局部实现细节。影响需求含义、接口、数据或权限的不确定性，以及缺资料或能力不足，必须报告 NEEDS_CONTEXT/BLOCKED 交回主控。主控补方案或重新拆分，不自动升级模型。高低模型由用户选择，不根据名称猜性能或价格。
- 有前置依赖的任务等前置任务验收后再启动。同一路径在待评审时仍被保留，避免验收期间又被改写。
- 子 Agent 自称完成只是报告，不能代替主控实际验证。
- 验证输出只证明工具执行的结果，仍需主控判断是否符合每条要求。
- 只报原任务内会影响正确性和达标的问题，达到标准后停止返工。
- `stop` 只表示取消，必须提供原因；正常返回自动释放，不能用取消冒充完成。整计划 cancel 须提供 reason 和本会话新增真实用户消息 messageId，无原因调用不取消、不自动重试。单任务故障只影响本任务及其依赖项，无关任务继续，模型错配仍暂停后续派发。宿主中断保留原计划；真实继续消息关联为 continue 后接续，或用 delegation_run 继续，插件先确认旧执行已清理，再恢复未完成部分。已返回报告继续验收，服务失败须处理后明确 retry；取消不覆盖报告、证据和真实失败原因。
- 聊天、验收页和导出均读取 `plan.completion`。模型提前说完成不能改变状态；后续明确重试会使当前回执失效，历史回执保留。
- 任务卡验证参数必须符合当前 DSH schema；原生 `read` 使用 `file_path`。派发前会预检必填字段，预检失败不会启动子 Agent。

详细主控流程见 `references/orchestrator.md`；执行者报告格式见 `references/worker.md`。
