# DSH Agentrix

小任务直接完成并验证；根据实际范围、风险和可并行工作决定是否委派，不因评分或操作次数强制派单。

插件提供 direct/delegate/delegate_parallel 路由建议，评分仅作参考，主控读实际代码后作决定。实际是否启动子代理以任务状态为准；任务卡决定边界、依赖和审查要求。

主对话输入框上方的小状态标签显示实际工具与模型活动，点击看详情。准备读取后，用 `delegation_decide({mode:'direct'|'delegate',reason})` 正式记录选择和具体理由；选择直接执行也要记录，系统建议委派时须解释为何直接做更合适。建计划可用 `decisionReason` 一并记录委派理由，省去单独工具调用。普通正文不能代替记录，不解析内部思考；“继续”沿用，补充范围后更新。遗漏时最多自动提醒原主控一次，不要求用户点击继续，不新开分类代理。只读任务最迟结束前记录；纯文字问答不强制补流程。阶段变化、等待或阻塞时简短说明当前动作和下一步。最终交付结论来自程序回执。

直接执行时，文件修改失败必须核对原文件并修复；成功读取或生成另一份文件不能代替原修改成功。程序最多提醒原主控补救一次；仍未解决时如实说明未完成项，不再声称全部交付。修改成功后也要核对实际内容是否满足用户要求。

## 执行顺序

1. 结合前文和相关代码，明确目标与可验证的子任务。短句和系统低分都不能证明任务简单；发现跨模块、多个功能或执行步骤增加时主动拆分。“继续”“可以，开始修复”承接原任务，不重新当成简单请求。
   准备读取用 `read/grep/glob`；目录和 Git 基线用 `delegation_inspect({operation:'list'|'git_status',directory})`。准备记录用 `delegation_note({kind:'task_plan'|'findings'|'progress',content})`，目录由插件确定并返回，不占业务操作额度。不得把任意业务文件命名为计划文档来绕过委派，也不要反复尝试被阻止的未知 shell。
2. 直接执行时先记录 direct 并完成验证；委派时调用 `delegation_plan` 提交任务卡及 `decisionReason`，或先记录 delegate。字段和示例见 `references/task-card.md`。不要并行调用判断工具和业务修改，须等保存成功。
3. 主控使用对话框选择的高模型做规划与最终验收，先确定复杂需求的方案、接口与验收标准，再拆给执行者。`complexity: routine/complex` 和 `complexityReason` 只说明复杂度与审查需要。执行者用 `models.worker`，未选则暂停。独立审查无需配置，使用该次任务派发时记录的主控模型与思考强度，保持独立上下文；切换聊天模型不改变已派任务的审查。主控自动派单只走 `delegation_plan/run`，不可走原生派单绕过模型与验收。
4. 调用 `delegation_run`。插件检查执行模型，复杂任务还校验分发者的审查模型，再按依赖、写入范围、并发与启动预算派单。默认每计划最多启动 64 次（首次、返工、独立审查都计入，可配置 1~256）；预算耗尽不反复 run。执行配置失效时重新选择并保存；审查服务失效时恢复已记录的分发者服务后明确重试。不会偷偷换模型；任务尚未启动时不消耗执行次数。
5. 短任务只提交最终报告。长调查、阶段转换或阻塞时，执行者或只读审查者可用 delegation_checkpoint 记录结论、下一步和成功 callId，记录不能替代验收。delegation_report 通过工具管线确认后自动结束并通知主控；不用 send_message 交成果，不再修改产物。缺上下文或阻塞先处理原因，有疑点由主控说明处理意见。状态默认只读摘要，完整内容用 delegation_status({taskId,detail:'full'}) 按任务读取。
6. 对 `review` 状态任务调用 `delegation_verify`，主控亲自执行任务卡中的文件读取与命令。严格模式下也允许。
7. 新建 complex 任务自动安排一个独立只读审查者，同时检查需求和质量，审查通过后主控才可验收。普通任务可按风险用 `delegation_audit` 请求独立审查。两种审查均沿用该次执行的分发者模型并计入同一并发与启动预算；失败后用 `delegation_audit({taskId,message})` 明确重试审查，不重跑实现。返工派发新执行时记录新分发者；审查重试仍用原记录。
   阅读实际结果，用 `delegation_review` 逐条引用证据验收；返工引用已有 `issueIds` 或提交 `issues`（criterion/severity/finding/真实验证 callId）。minor 不触发返工，复查只检查原问题和修复引入的回归。routine 返工后用 `resolutions` 引用新验证证据确认问题解决。测试通过不能替代视觉还原或实际场景证据。
8. 最后一次实际验收通过后，插件自动生成交付回执并结束回合，无需模型再写总结。有缺失步骤时最多两次提醒原代理，计数持久化，超限停止自动续跑。只有全部任务实际验收，回执才为“已完成”；失败、取消和未验收列出真实原因。模型的 403、404 等失败先处理服务或配置问题，不能通过重复调用或自动换模型掩盖。

## 责任边界

- 计划执行中主控不重复改写子任务产物；主控可以读上下文、监督与评审。
- 调用达到 80 次、运行达到配置的提醒时间，只在页面提醒并记录事件，不唤醒模型、不停止、不换代理、不消耗纠偏次数。Token 只统计；输出截断在原代理续接。重复同类失败通知主控，最多两次纠偏后仍重复故障才阻塞。长时间没有新活动只调查提醒一次；读取、流式输出和工具活动不会因没有写文件被误停。
- 子任务启动时固定模型；设置修改影响之后启动的任务。实际请求在发送前核对，错配会被阻止并暂停计划；不得自动换模型或新建 Agent 掩盖问题。
- 执行者遇到未定设计、缺资料或能力不足，必须报告 NEEDS_CONTEXT/BLOCKED 交回主控。主控补方案或重新拆分，不让执行者猜测或自动升级模型。高低模型由用户选择，不根据名称猜性能或价格。
- 有前置依赖的任务等前置任务验收后再启动。同一路径在待评审时仍被保留，避免验收期间又被改写。
- 子 Agent 自称完成只是报告，不能代替主控实际验证。
- 验证输出只证明工具执行的结果，仍需主控判断是否符合每条要求。
- 只报原任务内会影响正确性和达标的问题，达到标准后停止返工。
- `stop` 只表示取消，必须提供原因；正常返回自动释放，不能用取消冒充完成。失败或超时后不要无原因调用整计划 cancel，插件会在额度允许时沿用原计划恢复可重试任务；用户明确取消才传 reason。恢复的旧执行可用 `delegation_control({taskId,action:'stop',reason:'取消重载前未结束的旧执行'})` 清理，再明确决定重试。取消不覆盖已有报告、验证证据或真实失败原因。
- 聊天、验收页和导出均读取 `plan.completion`。模型提前说完成不能改变状态；后续明确重试会使当前回执失效，历史回执保留。
- 任务卡验证参数必须符合当前 DSH schema；原生 `read` 使用 `file_path`。派发前会预检必填字段，预检失败不会启动子 Agent。

详细主控流程见 `references/orchestrator.md`；执行者报告格式见 `references/worker.md`。
