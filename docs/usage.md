# 工具与运行约定

本页说明主控与子代理使用的工具、验收规则、记录和接口。安装与模型配置见 [README](../README.md)。

auto 模式先由主控比较委派收益与准备、汇报、验收的开销：已掌握上下文的小改或连续调整优先 direct，有独立执行量、隔离或并行价值时 delegate。选择理由要说明具体取舍；普通任务也可委派，不按字数、文件数或操作次数强制分流。执行复杂度看实际未决难点，新任务显式填写审查方式与理由，按错误后果选择是否增加独立审查；“要发布”本身不是复杂或高风险的充分依据。现有字段、兼容默认与 strict/fixed/off 规则保持不变。

工具结果的 `nextAction` 指明下一步。等待时简短告知用户，再调用 `delegation_wait` 或结束回复等待通知；验收后的依赖任务自动启动，无需重复 `run`。主控验证返回 C1、C2 等标准对照与短证据 `ref`；验收时逐条提交 `criterionId`、`finding`、`evidence:[ref]`，程序校验其归属和有效性，不代写通过结论。旧数字 `criterion` 和原始 `callId` 继续兼容。执行者报告参数不包含独立审查字段。

## 主 Agent 的工具

托管工具的 JSON 语法错误在 DSH 解析阶段进入 `agent/request-error`，尚未执行工具。插件只接管 `MALFORMED_RESPONSE` 中明确指向当前角色托管工具、且参数确实无法 JSON 解析的情况；通过原会话追加运行时反馈并让原模型在同一步重新生成，不修改坏参数后执行。主控的 `argumentRecovery` 保存在需求上下文，建计划前同样可用，并由 `/api/state` 的会话行返回；子代理保存在本次任务快照。最多自动修正两次，次数重载后保留，成功调用和状态查询不清零；`retrying/parsed/exhausted` 分别表示正在修正、参数已解析、已用尽自动次数，均不表示业务已完成。取消、报告已提交、模型服务错误及非托管工具沿用原处理。次数用尽保留原生错误；不自动重建任务、代理或模型。此机制不代替工具 schema、权限和实际证据验收。

| 工具 | 作用 |
| --- | --- |
| `delegation_models` | 与派发共用托管模型授权和解析检查；默认检查后续执行模型，可选 role: reviewer；taskId 查看启动快照，检查通过不代表服务商已响应 |
| `delegation_decide` | 主控提供 `relation: new/continue/update/question`；新需求或方案变化时提供 `mode: direct/delegate` 和非空 `reason`（最多 500 字）。多条待关联消息须给真实 `messageId` |
| `delegation_inspect` | `operation: list/git_status`，可指定 `directory`；通过原生工具管线运行固定的只读检查，每次最多显示 200 项 |
| `delegation_note` | `kind: task_plan/findings/progress` 和 `content`；保存本会话本需求的专用记录并返回路径，最多 64 KiB |
| `delegation_plan` | 新委派推荐携带 `relation/messageId/decisionReason/start:true`，一次记录、建计划并派发；省略 start 或填 false 仍仅保存 |
| `delegation_run` | 启动已有未启动计划，或明确处理问题后继续；合并派发后无需重复调用 |
| `delegation_wait` | 等待现有任务的报告、故障或用户新消息；原代理继续运行，不轮询模型、不消耗纠偏次数 |
| `delegation_status` | 无计划也可查询当前消息；默认计划摘要，可选 taskId，detail: summary/full；full 必须指定任务，只返回该任务完整报告和证据 |
| `delegation_checkpoint` | 执行者或只读审查者在长调查、阶段转换或阻塞时记录结论及成功工具证据；短任务只交最终报告 |
| `delegation_control` | `steer` 纠偏、`stop` 取消且必须提供原因、`retry` 有依据地重试；正常返回无需 stop |
| `delegation_verify` | 默认一次顺序执行任务全部检查，返回逐项证据；可用 checkIndex 单项重验，保留正式验收 |
| `delegation_report` | 当前执行者或审查者提交身份绑定的完整报告，工具确认后自动结束，主控不能代报 |
| `delegation_audit` | 请求独立审查；reviewPolicy 为 independent 时必须审查，未指定时兼容 complex 自动审查；失败后须给出原因处理说明才重试 |
| `delegation_review` | 逐条验收，或按问题编号、标准与实际证据返工 |
| `delegation_cancel` | 用户明确取消整个计划时提供 reason 和真实用户消息 messageId；无原因调用不取消、不自动重试 |

插件启用时，主控的自动派单必须经 `delegation_plan/run`；直接调用旧 `subagent/subagent_fork/spawn_teammate` 会收到明确的入口说明，避免绕过角色模型和资源限制。不替换原生工具定义，不干预其他插件的人工操作；关闭插件后恢复原生派单行为。

托管主控和执行者不使用原生 `list_subagent_models` 判断 Agentrix 配置是否可用，启用时会从对应工具列表隐藏该入口。统一用 `delegation_models` 区分授权检查、配置解析和实际请求：有原生会话白名单时，托管派发同样遵守，未授权在创建子代理前阻止；没有原生白名单时，按宿主配置调用的兼容方式使用用户保存的 Agentrix 模型，并标明 `agentrix-config` 来源，不伪装成原生授权。不会修改白名单或通过换入口放宽已记录的限制。当前状态接口提供 `modelRoutingPolicyVersion:1` 与每会话 `modelRouting`；其中 `not-checked` 仅为配置及授权状态，实际请求以任务 `modelRoute.actual` 为准。

多条“继续”消息逐条关联完后才自动恢复原计划。旧判断错误保留为 direct 时，可用 `delegation_decide` 的 `relation:continue,mode:delegate,reason` 明确修正，不必改成 update、添加虚假的新要求或重新建卡；没有新理由时只记录关联并给出下一步，不尝试失败的启动。`delegation_plan(relation:continue)` 复用原任务卡和档案，不用新传入的卡片替换旧计划。

当前需求进入托管计划后，主控和执行者的模型工具列表会隐藏 `team_task_create/update`、原生派单及 `wait_agent`；继续调用也不能创建、修改或勾选另一套任务。辅助看板仍可使用，`team_task_get/list`、`list_agents` 等只读观察保留，但观察结果和看板勾选都不能代替 Agentrix 的验收。子代理交报告后按现有事件通知原主控，无需额外等待工具或审批。

模型工具列表同时按角色收缩：主控不显示执行者的报告与阶段记录入口；托管执行者不显示主控的规划、调度、验证和验收入口；独立审查者仅显示读取、检索和报告入口。执行时仍检查身份及角色，隐藏入口不代替工具检查。

被拒写入、提前验证、错误报告等失败操作记录为计划事件，并通过 `plan.coordinationIssue` 返回具体原因和下一步；同一调用按 `callId` 去重，重复状态查询不消除失败。后续正确操作或对应任务阶段推进后标为已解决。误用工具不会取消原任务、重开代理或消耗纠偏次数。

`delegation_note` 的文件位于插件数据目录中的 `<运行状态文件名>.notes/<会话摘要>/<需求摘要>/`，只保存 `task_plan.md`、`findings.md` 和 `progress.md`。目录由插件确定，不接受业务路径；各层目录与文件均检查链接，写入采用临时文件替换。换需求使用新的目录，承接原需求继续使用原目录，不增加独立档案中心。

### 任务卡示例

以下是主 Agent 调用 `delegation_plan` 的参数。实际任务必须先读相关文件，再填写真实路径和命令。

```json
{
  "goal": "补充登录失败路径测试并核对结果",
  "relation": "new",
  "start": true,
  "decisionReason": "已有测试结构与预期结果明确，两条失败场景可由执行模型独立补齐；交接只需引用示例与接口，主控保留测试运行和验收。",
  "tasks": [{
    "id": "login-tests",
    "title": "补充登录失败测试",
    "instructions": "参考现有测试，补充密码错误和账号锁定场景；遇到实现缺陷先报告，不自行改实现。",
    "scope": "只改指定测试文件，不改业务实现和依赖。缺少必要信息时报告阻塞。",
    "outputs": ["tests/login.test.js"],
    "writes": ["tests/login.test.js"],
    "dependsOn": [],
    "complexity": "routine",
    "complexityReason": "按已有实现补充确定的失败测试，无需重新设计",
    "reviewPolicy": "independent",
    "reviewReason": "覆盖登录与账号锁定等权限边界，由独立审查核对覆盖范围，主控运行测试并验收",
    "criteria": ["覆盖密码错误和账号锁定", "测试全部通过"],
    "checks": [
      {"tool": "read", "arguments": {"file_path": "tests/login.test.js"}},
      {"tool": "pwsh", "arguments": {"description": "Run login failure tests", "command": "node --test tests/login.test.js"}}
    ]
  }]
}
```

验证步骤支持 `read`、`grep`、`glob`、`pwsh`、`bash`，参数遵守当前 DSH 工具定义；例如原生 `read` 使用 `file_path`，不能把旧示例中的 `path` 当成当前参数。计划派发前会读取当前工具 schema，缺少必填字段时不会启动子 Agent。只读任务的 `writes` 用空数组。不能用后台 shell 任务作为已通过的验证。

同类小修改合为一任务，保留每项标准和必要检查；只有独立判断、不同验证或并行价值才拆分，不按文件数量强制建卡。任务返回后，主 Agent 一次执行全部检查：

```js
delegation_verify({taskId: 'login-tests'})
// 必要重验时只执行一个检查，旧的单步返回格式保持兼容：
delegation_verify({taskId: 'login-tests', checkIndex: 1})
```

批量返回 `results` 中每项的 `checkIndex/ref/passed` 与真实输出摘要，顶层只返回一份 `criteria`；任一项失败时整体 `passed:false`，但保留每项结果。`checkIndex` 从 0 开始，验收标准可直接引用返回的 `C1/C2`。主控阅读返回结果后，在 `delegation_review` 的 `findings` 中逐条写明结论，`evidence` 引用该检查当前返回的 `ref` 或 `callId`。批量运行时禁止重入或提前验收，取消后不继续后续检查。重新验证同一步骤后，旧的两种编号都不能用于验收，历史仍保留。编造编号、缺少条目、验证失败、后台命令或无退出码的 shell 结果，都不能通过验收。

验证输出超过 2000 字符时，只在默认响应中显示摘要，原文保存在 `outputPath`。`truncated: true` 和 `readOutput` 会明确提示继续读取。主控可以调用 `delegation_status({taskId:'login-tests',detail:'full',checkIndex:0,offset:0,limit:4000})` 分段核查原文；`offset` 为从 0 开始的字符位置，按 `nextOffset` 继续，直到其为 `null`。每次最多返回 8000 字符。旧任务未保存原文时显示 `available: summary`，不补造完整结果。读取成功不等于内容符合要求。

跨会话等并发名额或写入锁时，主控使用 `delegation_wait` 或结束当前回复等待事件；正常排队不消耗补流程次数，不必反复查询，也不会因此停止自动派发。用户补充与取消仍可中断等待。

### 执行报告与独立审查

执行者结束前调用 `delegation_report({status,summary,report,reason?,concerns?})`。`status` 为 `DONE`、`DONE_WITH_CONCERNS`、`NEEDS_CONTEXT` 或 `BLOCKED`；后两项必须说明 `reason`，有疑点必须列 `concerns`。完整 `report` 最多 24000 字符，超限明确报错，不能静默截断。报告保存在任务档案的 `reports/<taskId>/`，实现与审查、不同执行次数分别存放。辅助档案暂时不可写时，必需的任务快照仍保留全文并提示记录问题。

新任务应显式填写 `reviewPolicy` 和 `reviewReason`（非空，最多 1000 字）。`coordinator` 由主控实际验证并逐条验收；`independent` 在此基础上增加独立审查。主控按错误风险和独立核查价值决定，不把执行复杂度当成风险：权限、破坏性数据操作、并发等高风险工作使用独立审查。只填一项或填写未知方式会在派发前报错；两者均省略时兼容旧流程，`complex` 自动审查，`routine` 按需审查。历史任务不改写审查合同，新字段保存在任务快照、状态摘要、页面与 Markdown 中。

需要独立审查的任务返回后自动排队；审查者只允许 `read/grep/glob` 和提交报告，禁止修改、命令执行或继续派代理。审查报告必须同时提供 `specVerdict` 与 `qualityVerdict`（`pass/fail`），以及具体 `issues`。审查未结束或有未解决重要问题时不能验收。审查结果是额外检查，主控仍须实际运行验证。测试通过不能代替视觉还原或真实场景验证。

普通任务可用 `delegation_audit({taskId})` 请求审查，重复请求不会重复启动。审查服务失败不会重跑实现；处理原因后用 `delegation_audit({taskId,message:'已处理的具体原因'})` 明确重试。每次执行对应的审查启动次数单独受现有 `maxAttempts` 限制，所有启动同时计入计划 `maxActivations`。模型不自动升级或切换。

只需配置执行模型。每次实际派发实现任务时，`task.dispatcherModel` 保存分发者的模型、思考强度、时间及对应执行次数。按 reviewPolicy 安排的独立审查、兼容任务按需或自动安排的审查及审查重试，都使用这份记录与独立上下文；切换聊天模型不改变已有执行的审查选择。返工派发新执行时记录新的分发者。旧任务没有记录时，在首次审查时记录当时的主控并注明 `legacy-review`，不补造过去的模型。已经启动的审查与历史路由保持原记录。

配置和状态接口通过 `reviewerModelPolicy: dispatcher-snapshot` 标识当前策略。旧 `models.reviewer/complex` 配置不再生效，读取时不改原文件；下次保存仅保留执行配置及兼容的 `reviewer:null`。新版配置页连接旧进程时提示等待自然重载，避免页面显示新规则而后台仍使用旧审查配置。

返工优先引用审查产生的 `issueIds`；主控新发现的问题用 `issues:[{criterion,severity,finding,evidence:[callId]}]`，允许引用实际验证失败的证据。`critical/important` 可触发返工，`minor` 仅记录。同一次执行中标准、严重度、说明与证据完全相同的问题只保留一个编号，证据不同的记录不合并。纯修复保存 `reworkContext`，向执行者和复审者提供原问题、相关标准、前次报告及本次修复报告路径，不重新发送完整说明和无关标准；新用户要求加入时仍完整检查。独立复查必须对原问题逐条返回 `ADDRESSED/NOT_ADDRESSED` 和证据；范围外发现只能作为可选建议，重要新问题必须说明由本次修复引入。主控最终验证与验收仍覆盖全部标准，不因复审范围缩小而跳过要求。由主控验收的任务用 `resolutions:[{id,status:'ADDRESSED',evidence:[新callId]}]` 确认修复。

历史任务未记录这些字段时保留原验收合同，不补造审查结果；新任务执行者未提交结构化报告会暂停，不能凭一段“已完成”通过验收。插件自然重载后新计划使用本流程；不强制重启宿主。

### 程序控制收尾

新计划采用协议 2。子代理用 `delegation_report` 交成果，通过实际工具结果管线确认后结束回合；`delivery: caller` 由插件通知原主控，成果不经 `send_message` 提交。报告失败不能进入待验收，成功提交后不能继续修改交付物。返回的子代理自动释放，`stop` 仅表示取消，必须提供 `reason`；取消记录来源、原因和时间，同时保留原失败、报告与验证证据。已验收任务重复清理保持原结果。

`agent/turn-stopping` 检查遗漏步骤：未交报告时提醒原子代理；主控仍有任务运行时等待事件。正常报告返回使用结果通知继续验证验收，不消耗补流程次数。主控在任务状态及成功验证结果均未推进的同一阶段最多补流程两次，子代理每次执行最多补报告两次；计数与阶段持久化，查询、重复 run 和重载不会重置。实际阶段推进后，主控后续遗漏使用新阶段的计数。超限保留真实未完成原因，不自动新开代理；用户取消不自动唤醒。

最后一次实际验收成功后，插件生成 `plan.completion`，准备 `plan.delivery`，在主控结束检查中先写入带 Agentrix 来源标记的交付记录，再结束回合；不新增完成工具，也不增加模型总结请求。回执包含结果、验收数量、交付物、真实证据及未完成原因，聊天、验收页和 Markdown 共用。全部验收才显示“已完成”；测试有结果但未验收仍是未完成。全部剩余任务取消显示“已停止”，部分通过其余取消显示“部分完成，其余已停止”。明确重试会使当前回执失效，历史回执保留。

主控可在 `delegation_review` 中提供 `delivery: {summary, inlineFiles}`。`summary` 是面向用户的交付说明，最多 2000 字；用户要求直接看文章、报告等正文时，`inlineFiles` 指定本计划 `outputs` 中的文件，程序展示已验收内容，主控无需重写或重复粘贴。文件入口调用 DSH 原生文件打开接口，正文在聊天末尾直接展开。单文件内嵌预览最多 128 KiB，超出时明确显示预览提示并保留完整文件入口；该显示范围不影响任务执行或原文件。

`plan.delivery.status` 为 `pending/delivered/failed`，分别表示准备发送、已写入会话、写入失败。发送失败保留验收、产物与证据；继续同一会话时只补发已有交付，不重开子代理。交付记录具有固定消息编号，重载后先检查原生消息记录，防止重复发送。历史任务不会自动补发；新交付按原会话与回复序号关联，后续需求不会把旧产物移到新回复下面。`GET /dsh-delegation-first/api/delivery?sessionId=<会话>&seq=<回复序号>` 只查询该回合的交付记录；`deliveryProtocolVersion:1` 表示当前宿主已加载该能力。

宿主可能先显示模型文字再触发结束检查，无法保证撤回已经显示的错误句子。完成标签与最终交付结论以程序回执为准，不匹配模型措辞判断成功。

协议 2 的计划没有 `plan.completion` 时，聊天输入框上方持续显示“尚未完成”及执行中、待验收等真实状态；回复旁扩展区可用时同步显示。验收页同时列出尚未解决的操作问题。`/api/state` 返回 `coordinationPolicyVersion: 2`、验收页显示“协作执行策略已生效（v2）”，才表示当前宿主进程已加载本轮修复；旧策略显示等待加载。仅更新源码不代表已经生效，等待自然加载，不强制重启已有任务。

### 持续执行与监督

插件记录工具与模型活动、成功证据、阶段结论及用量。短任务只要求最终报告；长调查、阶段转换或阻塞时再用 delegation_checkpoint 记录。独立审查者也可提交只读核查结论，阶段记录不能替代验收。

阶段证据按当前子任务的本次执行校验。最近活动只展示 16 条，完整调用元信息索引单独保存，较早的成功调用仍可引用；失败调用、其他子任务和返工前的旧调用不能引用。内部索引不随状态接口或模型详情反复传输，历史缺失的工具记录不补造。

相同工具错误连续出现时通知原主控，处理实际原因后向原代理纠偏；两次纠偏后仍重复同类故障才阻塞。长时间没有新活动只提醒主控调查一次，不停止任务、不占纠偏次数。持续读取不同文件、流式输出和工具活动不会因为没有文件修改被误判为停滞。

模型请求达到 80 次、运行达到 taskTimeoutMinutes（默认 120 分钟）时，只在页面提醒一次并记录事件，不唤醒主控模型、不终止、不换代理。Token 只作统计，保留 DSH 与服务商自身输出配置；max-tokens 在原代理续接，不消耗补报告次数。正式报告必须经实际工具管线确认成功，才进入审查或验收。

写入冲突按任务声明的实际目录检查。例如 workbench/** 只保留 workbench 目录范围，不会阻塞另一个项目的目录。同一目录中正在执行或等待验收的任务仍保留写入范围；验收或取消后释放。已取消计划不再显示旧的排队提示，也不会因修复自动恢复。

## 状态与资源限制

任务正常经过 queued → starting → running → review → accepted。失败进入 failed，模型错误、重载或启动额度耗尽可进入 blocked，取消为 cancelled。调用次数和时间提醒不改变任务状态。返工重新执行，仍受执行次数和启动次数限制。

子任务运行失败时，从原生 `turn/end` 事件保留真实原因，显示在任务面板、状态工具和主控提示中，并随任务保存。403、模型不存在等问题需要先解决服务或模型配置，再由主控说明依据后重试；插件不绕过服务限制，也不自动替换模型。已有历史任务中只保存了 `error` 的记录不会凭空补出原始原因。

- 同一 profile 的运行缓存最多保留 12 个会话计划；空间满时只移出已完成或已取消的最旧计划，其独立档案仍保留。
- 每计划最多 16 个任务，每任务最多 4 个验证步骤；新计划输入最多 64 KiB。
- 报告、工具输出和证据条数有上限，面板不保存完整对话或思考过程。
- 每个活动任务有独立的计时器和取消控制；不轮询唤醒子 Agent。
- 计划档案保存 `routing`、路由提醒和 `activationBudget`（已用、上限、剩余），面板和 Markdown 摘要都显示这些字段。
- 插件卸载、任务结束或取消时调用原生 activation 的 dispose()；运行时间提醒不释放资源。
- 配置页每 3 秒只读取配置；会话验收页每 3 秒只读取当前会话状态。未完成的请求不叠加，请求 8 秒超时；切换会话时重新挂载，旧请求取消，旧结果不会覆盖新会话。
- 侧栏提醒每 15 秒读取本地配置，并订阅共享模型目录；不读取任务历史或轮询模型服务，卸载插件后停止。页面保存后立即更新提醒。

配置保存到 `<DSH_HOME>/delegation-first/<profile>.json`，任务保存到同目录的 `<profile>.runs.json`。未设置 `DSH_PROFILE` 时使用 `default`；已有 v1 配置保留模式和预算，其余字段取默认值。文件通过临时文件加重命名写入，任务写入串行并合并中间更新。恢复失败会展示错误并保留原文件。

## 执行记录与会话导出

必要运行状态以 `<profile>.runs.json` 为准，其中包含原始需求关联、当前报告、验证证据和验收结论。新辅助记录位于配置文件旁：

~~~text
<profile>.runs.archive/.agent-tasks/<创建时间>-<唯一编号>/
  task.md          可读摘要
  task.json        结构化任务快照
  events.jsonl     追加保存的关键事件
~~~

摘要包括目标、任务说明、模型和子 Agent、声明的交付物、验收标准、当前报告、实际验证证据、主控结论和未完成项。它根据现有任务状态自动生成，手工修改摘要会在下次生成时被覆盖。

创建、派单、返回、失败、验证、纠偏、返工、重试、停止、验收及中断均由插件记录。返工前的报告和验证证据保留在事件文件中；摘要显示当前结果。普通成功工具活动只更新最近活动，按一秒合并保存运行状态，不逐次重写摘要；打开当前任务档案时会刷新摘要。

不再提供独立的历史中心、档案预览和下载面板。插件在聊天显示程序交付回执，用户通过“分享会话”整理和导出完整记录。验收页提供 Fleet、分享和聊天的原生页签入口；对应页签未启用时，按钮禁用并提示检查插件设置。

已有 `.agent-tasks/` 项目档案保留原路径。旧档案查询接口继续兼容读取，索引按每页 20 条读取；日常状态刷新不扫描历史，不读取完整会话日志。

已有快照不补造原始需求或历史。重启后的活动任务仍按现有规则阻塞，先清理旧子任务再重试；读取记录不会自动续跑。辅助档案写入失败时在对应会话显示提示，必要运行文件已保存的调度继续；必要运行状态保存或恢复失败仍阻止派单。

本功能只记录通过本插件建立的托管计划。简单任务以及其他工具单独创建的子 Agent，继续按原有方式处理。没有增加常驻模型循环或独立规划框架。

客户端已更新、服务仍运行旧版时，会按完整会话编号筛选旧版响应，并提示重新加载插件；明确返回其他会话编号的响应不会显示。首次读取失败提供“重新读取”和“回到聊天”，具体原因可展开；后续刷新失败保留上次结果，并标注尚未更新。

单任务故障只影响该任务及其依赖项，无关任务照常执行、排队和验收；模型路由错配仍暂停后续派发。处理真实失败原因后，主 Agent 对具体任务用 `delegation_control retry` 明确重试，仍受“每任务最多执行”和启动预算限制。宿主中断保留原计划与成果；用户明确继续后用 `delegation_run` 接续，或将真实消息用 `delegation_decide(relation:'continue')` 关联原需求后自动接续。插件先确认旧执行已释放，已返回报告继续验收，已验收任务不重复执行；不会借恢复原样重试服务错误。用户明确取消整个计划须提供原因及本会话新增真实用户消息编号，取消记录保留。

## HTTP 接口

- `GET /dsh-delegation-first/api/config`：配置。
- `POST /dsh-delegation-first/api/config`：保存模式、预算、并发、执行次数、运行时间提醒与模型。
- `GET /dsh-delegation-first/api/state?sessionId=<会话编号>`：仅返回指定会话的计数、计划、需求来源、模型、验证和辅助档案提示。省略参数保留旧版全局读取兼容。
- `GET /dsh-delegation-first/api/history?before=<档案编号>`：按创建时间倒序读取历史索引，最多 20 条；返回 `next` 游标。
- `GET /dsh-delegation-first/api/archive?id=<档案编号>`：读取指定任务快照和 Markdown 摘要。
- 同一档案接口加 `format=markdown`：下载摘要。接口只接受生成的档案编号，不接受文件路径。

路由仍通过 `ctx.inject(['webServer'], registerRoutes)` 等待服务就绪后注册，避免启动顺序造成的 404。

## 自动分流、状态和用量

`/api/state` 的 `coordinatorProgressVersion: 1` 表示当前进程提供主控直接执行进度。每个会话的 `execution` 保存当前回合的模型、工具活动、目标、最近结果和未解决的文件修改失败；`delegationAvailability` 按实际请求头检查委派工具是否可见。输入框进度区直接读取这些字段，不新增模型请求。插件服务返回 404 时前端显示服务不可用，不继续把旧记录当成当前进度。

`decisionProtocolVersion: 2` 和 `requestBindingVersion: 2` 表示当前进程由主控确认消息关联。`pendingMessages` 是尚未判定的真实消息，不能当成新增需求或补充；`messageResolution` 保存主控确认的 `relation/messageId/requestId/model/at`。`new` 从真实消息建立新需求；`continue` 和 `question` 不改变范围或执行决定；`update` 更新原需求范围或方案，托管补充仍须通过原有 steer/rework 流程落实。新需求不取消旧代理、覆盖旧计划或改变历史验收；同一会话仍只保留一个当前托管计划，新计划须等旧计划结束。

主控管理工具的 `context` 提供本会话当前需求、执行决定、消息关联结果和 `pendingMessages`（正文及真实 `messageId`），默认摘要也保留这些信息。`delegation_status({})` 在尚无计划时返回 `plan:null`，仍可查询和处理消息。多条消息未指定编号或编号无效时，错误直接附本会话候选；逐条用 `delegation_decide` 判断关系，不盲选最后一条，不扫描全局任务文件或其他项目会话寻找编号。

按返回结果最外层的 `nextAction` 行动：未关联消息优先为 `resolve_message`；消息已关联、当前需求尚无对应计划时为 `handle_request`（沿用已确认的 direct/delegate）或 `decide`（尚须主控判断）。同一会话还有未验收的旧计划时，新委派须先按返回步骤处理旧计划，不能同时建立第二套计划。`context.planMatchesRequest:false` 表示附带的是另一需求的计划；其完成回执只作历史背景，不表示当前需求完成。消息关联保存在会话记录中，历史计划与导出档案不附加后来收到的待处理消息，也不改写原验收结果。

已有计划运行时，新需求经主控确认为 `new/direct` 后，可处理不重叠的文件；显式文件目标与旧任务尚未验收的写入范围重叠时仍会拦截。新需求结束不会触发旧计划的补流程，旧任务按原通知机制返回并验收。任意 Shell 脚本不作路径解析，`writes` 是协作范围与并发排队依据，不是操作系统文件沙箱。

`decision` 保存执行方式与理由，`decisionCurrent` 表示当前消息均已关联且执行决定对应当前范围。业务写入、通用 shell 执行前须有 direct 记录，新计划启动前须有 delegate 记录。原有 strict/fixed/off 语义保留。模型只能引用本会话真实消息，不能伪造来源；多条待处理消息必须明确 `messageId`。普通正文不参与判定，也不解析模型内部思考。缺少判断首次拦截时，原生工具结果会立即向原主控附带纠正提示和真实消息编号，不必等主控结束才补救；尚无已确认需求时明确使用 `new`。补判断期间隐藏命令和写入入口，读取仍可用，判断保存成功后恢复。每条待处理消息最多自动提醒一次，计数持久化；取消后不提醒，也不自动重放旧命令。纯文字问答不强制补流程。

关联、执行决定和判定前暂存的用量保存在现有 runs.json。保存失败或尚在保存时不放行业务修改。主控在分类前的实际请求与用量先暂存，确认后归入对应需求；已发起请求不因后来收到消息而转移到另一需求，重复用量事件沿用原去重规则。历史缺失不补造。

页面分别显示主控选择和真实任务状态；决定委派或建立计划均不代表子任务已启动。新进程不再生成关键词评分、预计步数、并行数量或置信度；旧字段保持读取兼容。主控验证仅沿用宿主取消信号，取消仍有效，不再统一附加 60 秒超时；宿主工具自己的限制不变。

直接执行时，文件修改失败不会被读取成功或另一文件修改成功清除。结束检查最多向原主控注入一次补救提醒；同一需求继续时沿用失败记录和次数，新需求重新记录。成功修改原目标后清除对应失败；无明确目标的修改不靠其他成功工具猜测已恢复。用户取消、子代理回合与尚在托管流程中的计划不触发该提醒。这些直接执行状态只保存在当前进程中，不补造历史记录，也不生成托管验收回执。

auto 模式由主控结合实际范围、风险和上下文隔离价值决定是否委派；不根据关键词或工作量生成另一套分流判断。strict、fixed、off 保留原语义。托管计划继续隔离主控修改，并由实际证据验收。

管理工具默认向模型返回精简结果，完整任务快照与档案不截断。delegation_status({taskId,detail:'full'}) 只读取指定任务；默认摘要提供状态、未完成验证、关键证据和报告路径。

GET /dsh-delegation-first/api/state 增加 runtimePolicyVersion:2 和 requestUsage 数组（按 sessionId 筛选）。plan.usage 保存该需求统计，按主控、执行者、审查者及实际模型和执行次数分列；覆盖建计划前主控准备及直接任务。输入、缓存读取、缓存写入和输出保留宿主原始字段，不合并口径或估算费用。重试不清零，重复事件去重，重载恢复；历史、缺失或尚未返回请求标记统计不完整。原 task.supervision.metrics 仅作兼容，不代表完整需求用量。

源码更新后等待宿主自然重载；页面依据运行策略版本提示是否已经生效，不强制重启。

## 执行中的补充与服务错误

“任务验收”页是当前会话的只读“专注群聊”看板，不提供输入框或派发操作。主控判断、工具活动、阶段记录、报告和验证结果分别标明来源，可按成员筛选，轮询不重复添加同一记录。默认显示最近 20 条，上方“查看更多”每次向前展开 20 条，并标明当前快照中剩余的条数。各成员筛选分别记住展开范围；刷新和新活动保留已展开记录，查看更多时保持原阅读位置。只展示当前快照保留的近期记录，完整报告与证据在任务详情中；历史缺少时间或模型时不补造。成员、消息、提示和详情随整页统一滚动，不再各设滚动区域。任务详情默认收起，宽区域并排展开，窄区域切换到详情视图。切换需求后重置成员筛选、展开范围和详情，不把上个需求的执行活动混入新需求。阅读旧记录时保留滚动位置，可用“回到最新活动”继续跟随更新。

每个执行者的计划交付文件与执行报告、独立审查者的审查报告分别列出，不再藏在技术详情中。聊天任务手风琴、验收页的成员视图、报告旁和任务详情均可查看文件位置；验收页支持复制路径。相对交付路径按该计划的项目工作目录定位；缺少完整目录时保留原路径并说明。计划路径不表示文件已经生成，已提交报告也不表示已验收；没有记录的路径明确显示未记录，不补造交付物。

多 Agent 聊天详情按任务分组为手风琴，每项收起时展示任务名、状态和当前角色的模型。展开可见执行者与独立审查者各自的活动、最近工具和报告摘要，以及任务范围、异常原因和主控验收情况。默认展开第一项，允许同时展开多项；轮询刷新、任务阶段变化及主控恢复执行时保留用户选择。主控判断放在清单后的折叠区，异常保留在对应任务内。

托管任务正常执行时，聊天输入框上方的常驻区域持续显示协作进度，不等主控输出最终回复或宿主生成回合尾部节点，也不需展开思考。内容来自现有任务与工具事件，包括任务名称、当前工具或模型活动、运行时间、最近工具及结果、排队或待验收原因；阶段结论标明由执行者提交、尚待核实。当前活动与最近已结束的工具分别展示，不用调用次数推算完成百分比，也不为进度增加模型请求。主控开工、派发、阶段变化、等待或阻塞时，还应在主对话用一两句说明当前动作及下一步。异常提示与交付回执仍按原规则展示。

用户在执行中补充信息时，原主控会从等待状态恢复，处理原消息；不会重复注入，也不会重开执行者。验收页与聊天进度显示待处理条数，处理记录保留原文、对应任务、处理说明和新增验收标准。主控通过 `delegation_control` 的 `steer` 关联 `inputIds` 与 `additionalCriteria` 同步要求；纯答复用 `acknowledge`，已返回的结果如需修改则使用关联补充的 `delegation_review rework`。未处理的补充会阻止验收，已撤回的消息不阻止。

计划与当前需求按 `source.messageId` 关联，同一会话内的前后两项需求分别展示。当前需求未委派时显示其原文和未启动子代理；其他需求的计划只在折叠的历史区显示，原快照、回执与导出保留。主控提示不带入其他需求的计划；关联信息缺失时明确提示未确认。有匹配的正式计划时，页面主区显示主控确认的复杂度、理由和实际执行安排；旧版规则评分仅作为历史信息保留，新需求的复杂度和执行安排由主控根据实际任务确认。

思考强度未显式配置时，首个请求可采用宿主请求头记录的同一模型默认值，并固定到该次执行；显式配置、服务商或模型错配仍在发送前阻止。

`QUOTA/429` 明确显示为对应模型的服务额度或限流问题，保留原始错误、报告和证据。插件不能恢复服务商额度，也不会自动切换模型或反复重开代理；恢复服务或手动调整模型后明确继续。无原因 cancel 不自动重试这类错误。`coordinatorIssue` 记录主控服务错误及恢复响应时间，主控恢复后继续验证已有结果。明确取消的计划不会自动恢复。

明确的 `Illegal API invocation from an unapproved channel` 记录为 `MODEL_SERVICE_REQUEST_REFUSED`，表示该次请求被服务商拒绝，不等同于模型配置失效或所有请求均不可用。保留模型路由、原始原因和证据；主控须先核对服务商支持的调用方式与限制，处理后明确重试失败任务。普通权限错误、所有 403 或仅有 `11128` 不会被笼统归入此类。已有执行者继续运行；无原因取消不能触发自动重试，也不能在其他任务仍运行时生成终局回执。

运行与异常可以同时存在。聊天紧凑条同时显示执行数、请求被拒或失败数、验收数；展开后同时保留运行任务的当前工具、最近活动和异常说明。原始服务错误放入可展开的详情，不直接占满主要提示。旧任务只有原始通道拒绝文本时，前端仅改善其说明，不改写历史状态、报告或验收结果。
